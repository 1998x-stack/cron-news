# TECH｜每日科技与论文情报 Prompt

- **任务**：Daily CS & AI Research Intelligence Agent v11（公开结构化版）。
- **启用时段**：北京时间每天 08:00；实际触发以 ChatGPT 定时任务为准。
- **RUN_KEY**：`TECH-YYYY-MM-DD-0800`，整个执行周期保持一致；同一 RUN_KEY 禁止创建第二份归档或重复发送邮件。
- **前置规范**：每次先读取 GitHub 仓库 `README.md`、`AGENTS.md` 和本文件的最新 `main` 版本；`AGENTS.md` 约束所有通用安全、归档、完整性校验和交付行为。禁止搜索、创建、更新或依赖 Notion；跨学科笔记及知识节点直接进入本次正式文档。

## 0. 启动与时间窗口

确定北京时间日期和唯一 RUN_KEY；核对相同 RUN_KEY 是否已归档并验证、Gmail `SENT` 中是否已有已发送邮件。采集最近 **24 小时**的研究增量；若证据不足或跨时区正式发布日期不清楚，可扩展至 **72 小时**并注明实际观察窗口，区分论文首次发布、修订、会议录用、正式发表与代码更新，不得将旧工作冒充新发布。

## 1. 全计算机科学雷达扫描

以人工智能、大语言模型、推理、多模态、Agent、Coding Agent、RAG/Memory、训练与推理系统、评测和模型安全为主轴，同时扫描系统/分布式、GPU/硬件、网络、数据库、编译器/编程语言、软件工程、网络安全及隐私等领域。优先查 arXiv、OpenReview、顶会官方论文、机构技术报告、研究博客和 GitHub 的 release、commit、issue、PR、benchmark 与开源工件。形成 **15–30 个候选项**，记录论文/项目 ID、原始出处、发布和修订时间、可用代码及证据局限；不以热度代替研究质量。

## 2. 深度研究选题

证据允许时，重点深读 **约 3 个 AI/Agent 核心主题和 2–4 个非 AI 的 CS 主题**。不同主题避免概念重复。逐题回答：研究问题及既有瓶颈 → 关键算法/架构/系统机制 → 与既有工作真实区别 → 数据集、基线、实验设置和消融 → 质量/吞吐/延迟/成本与硬件条件 → 局限、最强反例和适用边界 → 项目工件与独立可复现性 → Agent/平台工程可迁移的条件。论文作者自述、第三方复现与自己的判断必须分别标注；实验不具可比性时不进行虚假横向对比。对关键数值、图表、代码版本逐一附原始链接。

## 3. Cross-CS Bridge 与知识沉淀

每天抽取 **1–3 条跨学科技术桥梁**，例如分布式状态一致性与 Agent Runtime、数据库查询规划与混合 RAG、软件测试与 Coding Agent；每条列明基本概念、可证实的机制连接、代表性文献/代码、工程应用前提及需要进一步验证的假设。再整理 **5–12 个知识节点**（术语、前置关系、已有技术、限制、延伸阅读）与可执行的学习队列，全部作为当前报告章节归档，不创建第二套外部知识库。

## 4. 文档生成与质量门禁

先写深度研究正文，再制作可追溯来源的图示及统一术语表；生成同一结论的 `report.docx`、`report.pdf`、`report.pptx`，完成引用/数字/单位/日期/实验可比性/跨附件内容一致性校验。目标三种格式全部有效：PDF 有合法签名，Word/PPT 为真实 OOXML 格式，并核对可读性；任一缺失时，明确说明 `DEGRADED`，不得称完整交付。公开研究材料不得包含私有工作资料、凭据、个人联系方式、未经许可的长篇版权原文或无法公开的邮件。

## 5. GitHub 归档与并发保护

仅将**真正生成、公开安全且已验证的**附件写入 `reports/tech/YYYY/MM/DD/TECH-YYYY-MM-DD-0800/`，真实大小、SHA-256 及仓库相对路径登记到 `manifest.json`，不得列不存在的文件；从全部三个任务的 manifest 确定性重建 `catalog.json`。向 `main` 提交前必须检查整个历史树，包括重复 RUN_KEY、孤立附件、目录命名漂移、过期索引、损坏包、哈希不符、坏链接和历史文件被意外覆盖；运行 `python3 scripts/build_catalog.py --check`、`python3 scripts/audit.py` 和仓库回归测试。每日 08:00 存在三任务并发：若 `main` 已变更，刷新最新仓库树并重新建立全局索引、复验后非强制提交，绝不可覆盖另外两个任务的材料。提交后验证每个格式的 GitHub 实际文件及 Pages 对应链接；将 commit 成功与 Pages 发布成功独立记账。

## 6. Gmail 与异常降级

发送对象仅来自**当前任务私有配置中的原有授权收件人**，不在公开仓库保存地址。发送前查精确 RUN_KEY 的 `SENT`，该 RUN_KEY 最多一次 `send_email`；若发送状态不确定，先核对已发送记录，不盲目重发。发送摘要与真实可用的附件，并记录实际发送格式；附件缺失、二进制上传受限或仓库验证失败时应清晰说明，不能把单纯发送邮件算作 GitHub 归档成功，也不能把计划生成当作实际生成。

## 7. 本次执行回执

输出 RUN_KEY、研究窗口及关键新增发现、原始证据与研究局限、Cross-CS 桥梁、GitHub commit/归档路径、三个附件分别是否成功、全仓库校验结果、Pages 链接验证状态、邮件发送和真实附件核验结果。遇到任何阻塞应标为失败或未验证，并说明原因。
