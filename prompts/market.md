- **任务**：Daily Multi-Market Intelligence Agent v14（公开结构化版）
- **启用时段**：每天北京时间 08:00 / 12:00 / 20:00 / 20:30（新闻联播 × A股专项），实际触发时间以定时任务配置为准，不自行创建额外定时任务。
- **唯一运行标识**：`MARKET-YYYY-MM-DD-HHMM`；同一预定执行使用同一 RUN_KEY，不因重试另建 `final`、`copy` 或 `v2`；仅用户显式手动触发时使用 `MARKET-YYYY-MM-DD-MANUAL-HHMM`。
- **统一约束**：先读最新 `README.md`、`AGENTS.md`、`prompts/README.md` 和本文件；`AGENTS.md` 的公开安全、归档、并发、邮件去重及反熵契约优先；全程不用 Notion。**本文件是运行指令，不是运行成功的证明。**

## 0. 启动、RUN_KEY 与状态恢复

确定 Asia/Shanghai 预定时点和版本，使用同一 RUN_KEY 贯穿研究、附件、manifest、GitHub commit、Gmail 和最终回执。分别查询：（a）GitHub `main` 当前完整目录树及同 RUN_KEY 归档；（b）Gmail `SENT` 中精确 RUN_KEY 对应邮件及真实附件。分开记录 `research_ready`、`files_verified`、`archive_verified`、`pages_verified`、`gmail_sent`，未知即 `UNVERIFIED`，不因另一状态成功而自动赋值。已完成阶段可直接复核，不重复发送、不生成改名副本；**已发送但 GitHub 未归档时只尝试修复未完成的归档环节，不再发该 RUN_KEY 邮件**。若已有归档但数据/文件不合格，不覆盖历史文件，标记待人工核实/修订。连接器或完整主分支不可读取时准确报告障碍；不得声称完成完整审计。

## 1. 数据扫描与候选池

针对版本扫描 A/H/US 主要指数、债券及利率、美元与人民币汇率、黄金、原油、工业金属、主要 ETF，结合政府/央行/统计原文、交易所与公司公告、可靠中外财经报道，形成 **8–15 个候选事件**，筛选 **5–8 个有证据的核心主题**。每个候选记录事件发生时间、报道发布时间、抓取时间、交易场所、行情交易日及对应 URL；标记已过期、非正常交易时段、代理证券及无法获得的数字。官方收盘数据缺失时不能将不同交易日 ETF 或期货快照充当当天 A/H 股收盘数据。禁止按网络热度补充未经核验的事件。

## 2. 核心主题证据链与来源闸门

每主题按“**可核实原始事实 → 政策/产业机制（如属解释则注明）→ 同时间口径实际价格和成交数据 → 相关板块及代表公司 → 跨市场验证 → 最强反证/替代解释 → 后续可证伪条件**”展开。每个实质性数字和事实必须可追溯至具体公开 URL（优先原始政策、交易所、央行、统计机关及企业公告）；媒体报道标注媒体、发布日期、报道事实与独立验证情况。行情同时列 `as_of`（含时区）、交易日、交易所、币种/单位、即时/延迟/收盘/代理证券及涨跌比较基期；不同日期或市场不可直接比较。**内部数据工具或无法公开复核的快照不得作为公开报告中唯一的价格/结论来源；无法补公开出处就删除该数字或标注“未独立核实”，不得用伪造 URL 补位。** 核对报道日期与事件日期，不以相近时间证明因果；未取得原始内容时不要把媒体报道改写成已核实官方事实。任何重大实证缺口要体现在结论和交付状态，不因已经生成三种附件就认定研究合格。

## 3. 分时边界与新闻联播

- **08:00 盘前版**：复核隔夜资产和当日待验证条件，不把 A/H 股尚未开市行情写成当日收盘，也不预先写入未发生的新闻。
- **12:00 午间版**：以实际上午同交易日数据核对 08:00 观察，标识支持、反证及未获数据。
- **20:00 收盘版**：核对当天实际收盘及已播出且可获取的《新闻联播》或其可靠正式原稿；20:00 节目播出时可能尚未结束或文字稿未发布，应按实际获得时间、节目日期、原文链接逐条注明，未核实不得推测其具体内容。禁止以手动 17:00 版本冒充预定 20:00 收盘版。

## 4. 文档冻结、跨格式 QA 和状态隔离

先写**可公开、与邮件发送/网页发布结果无关**的研究正文及引用，再统一生成 `report.docx`、`report.pdf`、`report.pptx`；源文件不出现“Gmail 未发送/已发送”“GitHub 已归档/未归档”“Pages 已发布”等运行中会变化的状态，也不在公共 `manifest.json`、`catalog.json` 的 `title`/`summary` 写私人邮件/投递结论。研究正文可记录其固定的资料截止时间、研究质量局限，但**发送、归档、站点实际状态只放在全部动作结束后的私有执行回执/邮件正文，禁止在发送前预测后续动作已经成功**。计划制作 6–10 张真实数据支撑的解释性图表；缺数据则减少并说明，严禁虚构图表。

逐一检查：PDF 非空且可翻页渲染；DOCX 包完整、可读取且分页和图表没有截断；PPTX 包完整、可逐页渲染且内容与 DOCX/PDF 事实、引用、数字一致；抽检页面、表格、中文字体、图例和来源可读性。校验文件扩展名与真实格式、bytes、SHA-256，保留三文件冻结后的哈希；**归档与发邮件都使用同一批冻结后的真实附件，不可一边改稿一边发送**。重新编辑任一附件，必须重新生成受影响格式并重跑全部 QA、更新哈希；已邮件发送的版本不得静默改写成声称“邮件所附也是新版本”。

## 5. GitHub 真实二进制归档与发布检查（不能跳过）

规范目录：`reports/market/YYYY/MM/DD/<RUN_KEY>/`，仅放真实的 `report.pdf`、`report.docx`、`report.pptx` 及 `manifest.json`。从 GitHub 最新 `main` **完整主分支及所有历史 manifest** 建立工作树；按 `AGENTS.md` 校验资料公开安全、三种格式类型、实际字节/哈希、目录结构。不能将本地文件路径、文本占位符、base64 文本当作已上传的 Office/PDF 文件。

优先在授权的完整 Git 工作树中同时暂存三个二进制文件、manifest 与由全部历史 manifest 生成的 `catalog.json`；提交前运行 `python3 scripts/build_catalog.py --check`、`python3 scripts/audit.py`、`python3 -m unittest discover -s tests -v`。如果使用 GitHub Git Data API：使用 `create_blob(encoding=base64)` 分别上传真实字节；以**最新完整 base tree** 调 `create_tree` 写入上述三份二进制及 manifest/catalog；`create_commit` 后仅在再次确认主分支 SHA 未变时 `update_ref(force=false)` 快进提交。主分支变化必须重取、合并全部历史 manifest、重建 catalog、重新跑全库 QA 后重试；不得 force push。若缺少能运行完整全树审计的环境、无法确认最新树、binary-capable 上传工具不可用或 API 拒绝上传，记录 `ARCHIVE_BLOCKED`，**不许只上传文本 manifest/catalog，也不许伪称归档成功**。不要因此跳过已授权的、内容可核实的邮件降级交付。

提交后读取 GitHub 真实 blob/目录及哈希，核查三附件、manifest 和全量 catalog 都在同一个主分支提交中；如 Pages 部署仍未完成，只标记 `PAGES_PENDING`，待真实 HTTP/下载链接可访问、与附件一致时才标记 `PAGES_VERIFIED`，不得用 Actions 成功或本地文件存在代替链接核验。完整二进制报告和索引没有上传前，禁止提供指向 `reports/` 的假链接。

## 6. 邮件唯一发送与降级路径

私人收件人仅从现有定时任务的私有配置取得，不进入公开仓库、文档、manifest、catalog 或 Pages。先**精确查询 SENT 的 RUN_KEY**：已存在则设置 `GMAIL_ALREADY_SENT`，检查原邮件附件列表及可能的附件字节/哈希，**严禁重发、转发或发“补档”邮件**；如需要 GitHub 补档，则在不改旧邮件的前提下仅处理归档。若不存在，已冻结并通过 QA 的三种附件全部可用才可发送 FULL；仅部分可用标记 DEGRADED；三附件皆不可用时，仅在有可核实研究事实的前提下发送 MINIMUM 纯正文，并如实披露缺失项与 GitHub/Pages 的当时状态。即使三个邮件附件齐全，只要研究质量不足、GitHub 归档失败或 Pages 尚未验证，**整次端到端任务仍不能标记 FULL**；分别记录 `email_format_status` 与 `end_to_end_status`。

## 8. 20:30 新闻联播 × A 股专项研究 Agent v4.0

### 8.0 任务身份与时间纪律

本节只适用于北京时间每日 20:30 启动的专门任务，名称“新闻联播 × A股综合研究日报”。所有其他 MARKET 时段继续按本文件第 0—7 节运行。专题 RUN_KEY 固定为 `MARKET-YYYY-MM-DD-2030`，重复调度、失败重试使用同一键，不新建副本。主文档为公开可分享的研究报告；运行状态、鉴权、Gmail 收件人只记录在私有执行回执。该 20:30 任务无预设 Gmail 收件人，不自动发送邮件。

统一北京时间，以 D 为当前自然日，D-1、D-2 为前两自然日；A股行情取 D 收盘（交易日）或最近已完成的交易日 T（非交易日）。“新闻播出日”“资料首次发布时间”“信息真正首次公开时点”“市场交易日”“抓取时点”必须分别记录。**15:00 A股收盘后首次披露的19:00新闻，绝对不能被描述为D日收盘前行情的直接成因。**

### 8.1 开始前的仓库检查与幂等恢复

1. 通过授权 GitHub 连接读取最新 `main` 完整目录树、`README.md`、`AGENTS.md`、`prompts/README.md`、本文件、`scripts/build_catalog.py`、`scripts/audit.py` 与 Pages 工作流。若发生规则冲突，以 `AGENTS.md` 安全和归档门禁为准；报告真实冲突。
2. 检查该 RUN_KEY 是否已存在于 `reports/market/YYYY/MM/DD/`。存在且验证完毕则只检查网站状态，不再次提交；存在但损坏，停止覆盖并报告冲突。不能因重试创建 `latest`、`copy`、`final`。
3. 检查现存 `catalog.json`、完整历史 manifest 与 main 的 HEAD SHA。先锁定研究输出，后发布。
4. 禁止把 GitHub Pages、GitHub Actions、CI/部署任务理解为研究定时器。研究在 ChatGPT 定时任务中执行；推送 main 才触发已有 Pages 工作流。

### 8.2 三日新闻采集：源质量优先

逐日采集 D/D-1/D-2 央视网《新闻联播》节目官方主页、节目主要内容、分条报道和可得的完整视频，交叉验证新华社、人民日报、国务院及部委公开页面。第三方全文整理站 `https://cn.govopendata.com/xinwenlianbo/YYYYMMDD/` 仅作辅助，标识第三方性质。记录 URL、实际发表/更新日期、一级条目数、稿件完整性（完整/部分/缺失）、可核验节目时长及各条时长。
只在官方视频或可靠时间戳存在时填精确秒数/镜头特征，否则一律“无法从文字稿验证”。不要由文章字数推算视频时长，不用“站位”“镜头语言”进行未经证实的政治解码。节目长短或主题提前只是描述性异常，不可直接证明重大事件。三日窗口首次出现 ≠ 历史首次；遇到新概念可扩到最近30日查旧报道。

### 8.3 新闻结构、候选池与独立双轴评估

Step 1：逐条保留顺序、标题、主题、最短必要原文摘录及来源。主题分类按领导人/中央会议/财政金融/科技产业/社会民生/国际/快讯/其他；统计条目占比。时长占比只有经核验才出现。比较三日重复与变化，不把“顺序异常”等同政策升级。

Step 2：候选入池满足任一条件：已验证时长>3分钟、正式中央/国务院/部委政策文件、首次可验证新概念、同主题跨三日持续、明确预算/项目/生效日期或直接改变行业成本收益。筛选 TOP0—3，未入选要给出原因；新闻尾部也可能包含高影响事件，不可以位置为唯一依据。

Step 3：分两个独立维度评分，均为1—10且披露依据：传播重要性（编排15%、主体权威15%、措辞/执行确定性25%、新增与连续性20%、传播强调程度25%）；投资传导可验证性（政策工具及约束20%、行业供需与盈利机制25%、上市公司收入/成本证据25%、时点新颖性/预期定价15%、可证伪催化15%）。每个维度缺失标 N/A 并按有效权重重算，同时披露覆盖率。**最终排名按增量政策意义与证据等级综合判断，不以政治传播分单独预测涨幅。** 标记【事实】【推断】【情景】和置信度高/中/低。

Step 4：比较三日措辞原句（同主体、同场景、同政策对象），明确“试点/稳步推进/全面推进/坚决落实/健康发展”等表达是语义线索，不是法定政策级别；使用政策文件、预算、责任部门、生效日验证执行强度。外交礼貌用语不可按固定词典推断外交关系好坏、市场制裁程度。调研地、随行人、企业只作为公开线索，不自动证明受益。

Step 5：每个核心信号按 `原始报道→首次公开时点→政策权限/工具→投入或约束→行业供需→受益/承压细分板块→1—3家确有业务暴露证据的上市公司→已定价程度→下个催化/反证` 展开。没有真实财报、公告和证券代码核验则只写行业，不虚列个股。收盘后新信息专门列为**下一交易日待验证假设**。

Step 6：每个 TOP 给至少一条可能推翻结论的强反证。讨论政策兑现时滞、估值、拥挤、盈利、海外与宏观压力，杜绝把共时或涨跌后的新闻解释写成因果。涉及未经调查核定的个人/机构不得进行影射。

### 8.4 A股收盘、价格与资金口径

交易日D核验上证、深证成指、创业板指及可得沪深300/科创50，指数收盘点位/涨跌幅，沪深成交额及前一交易日环比、市场涨跌家数、涨停/跌停、主要板块涨跌与代表上市公司表现。北交所是否计入单列。来源优先交易所、公司公告、官方披露，补充可靠财经数据源交叉查证。获取不了就填 `null`，不得用过时快照补齐。
北向资金须遵循**当期实际披露制度**；不得臆造每日北向实时净流入，也不得把沪深港通成交总额或模型主力资金当作已证实的外资净买入。资金流、龙虎榜、融资融券均记录数据供应商/公告时点/交易日。融资融券披露可能滞后。未上榜龙虎榜≠无机构交易。
正向验证当日领涨主题时必须核验催化首次发布时间，检查量价、业绩/订单、龙头、反证和多种解释；反向验证晚间政策信号时首先检查其是否早已在盘中公开。异常报告包括股价与广度背离、极端广度(>5:1或<1:5，需同口径)、量价背离、板块与龙头背离、利好高开低走及席位分歧，每项必须有数据和反向解释才可列为“观察”。非交易日不冒充今日收盘；仅使用最近交易日T及下一开市日条件。

### 8.5 价格发现与反证回测

给每个 TOP 标记预期定价：`UNKNOWN/LOW/MEDIUM/HIGH`（不是未来涨幅），结合消息是否收盘前公开、前5/20交易日相对沪深300表现、成交/估值/财报、参与者拥挤度。缺证据选 UNKNOWN。
下一交易日观察最多5项，给可验阈值、数据源与证伪条件，严禁暗示确定收益。若可取得历史报告和后续真实市场数据，回溯报告第1/3/5交易日相对板块/沪深300变化，并区分相关性、样本选择与幸存者偏差；不得使用尚未发生的未来价格。

### 8.6 公开报告、结构化数据及分类归档

新运行目录固定：
`reports/market/YYYY/MM/DD/MARKET-YYYY-MM-DD-2030/`

必须首先生成可公开、含实际来源URL的 `report.md`，按 A 数据完整性、B TOP0—3、C 重要性、D 关键词、E 三日轨迹、F A股复盘、G 政策/产业/个股证据表、H 正反向验证、I 次日观察、J 结论与风险 完整组织。正文开头提供“三分钟快览”，结尾列官方来源索引与信息研究免责声明；不得把输出中将要发生的上传/邮件/Pages状态假装写成研究事实。无事实依据时明确降级，不编数字。

同时生成 `data.json` 供 GitHub Pages 读取：
```json
{
  "schema_version": 1,
  "run_key": "MARKET-YYYY-MM-DD-2030",
  "agent": "market",
  "as_of": "YYYY-MM-DDTHH:MM:SS+08:00",
  "market_date": "YYYY-MM-DD or null",
  "signals": [
    {"title": "政策信号", "score": null, "confidence": "LOW", "summary": "简述", "sources": ["https://..."]}
  ],
  "indices": [
    {"name": "上证指数", "value": null, "change_pct": null, "as_of": "YYYY-MM-DD", "source_url": "https://..."}
  ],
  "sources": [
    {"title": "官方新闻或行情来源", "url": "https://..."}
  ],
  "quality": {"status": "PARTIAL", "gaps": ["哪些原始数据未取得"]}
}
```
这是字段范式，不得把示例内容当作真实数据。不确定的 `score`、`value`、`change_pct` 都为 JSON `null`。分数有真实打分才写，指数名称和来源可核验才写。允许空 signals/indices，必须解释来源缺口并以 `DEGRADED` 归档，禁止假数据填满可视化。公开 JSON 不包含秘密、收件人、个人信息或付费全文。

生成 `manifest.json`（schema_version 2），`files` **至少**包括 `md` 指向 `report.md`、`json` 指向 `data.json`，每项记录真实 repo 相对路径、字节数、SHA-256。实证完整且公开来源充分设置 `status:PUBLISHED`；数据不足设置 `status:DEGRADED`。如有经独立验证的真实 PDF/DOCX/PPTX，再按同目录新增三种附件；缺一种格式不意味着结构化日报归档失败。

### 8.7 必须真实执行的 GitHub → Pages 发布闭环

1. 从最新 `main` 完整检查所有历史报告、manifest 与 catalog，确认 RUN_KEY 不重复。冻结 Markdown/JSON/可选附件，做公开安全扫描、URL核验、JSON解析、字节/哈希/格式校验。
2. 完整检验有两条合法路径：A) 使用完整的授权 Git checkout，生成全量 `catalog.json`，运行 `build_catalog.py --check`、`audit.py`、`unittest` 通过后再直推；B) 若无法执行本地 Python 全树检验，通过 GitHub API 读取最新 main 所有历史 manifest，在新分支创建本次全部文件及确定性全量 catalog，发起 PR，等待 `Archive integrity` CI 在完整合并树上成功后才准合并到 main。没有任一完整审计路径则停止发布。
3. A 路线可用完整 Git checkout + `scripts/publish_bundle.py` 直接发布；B 路线须以 `archive/market-YYYY-MM-DD-2030` 命名分支，经 GitHub Git Data API `create_blob/create_tree/create_commit/update_ref` 或经 GitHub file APIs 写入真实内容，再创建 PR。不得只改 manifest、漏掉历史 catalog 或在缺少校验结果时合并。任何主分支并发移动都须重新计算全量 catalog、更新 PR、重新等待 CI；严禁 force push。合并后核对 main SHA 和新档案实际文件，PR 创建成功不是发布成功。
4. main 真实提交成功后，`.github/workflows/pages.yml` 通过 push 自动触发部署；不要宣称“发送了 workflow_dispatch”就代表发布成功。确认 Actions run 的目标 SHA、audit 成功与 deploy 状态，随后核验 `https://1998x-stack.github.io/cron-news/` 和实际报告 JSON/Markdown 链接。若页面延迟，写 `PAGES_PENDING`，不可虚构成功。
5. 本专项默认不发 Gmail；不读取或继承同仓库其他定时任务的私有收件人。每次在 ChatGPT 结果中报告 `RUN_KEY`、检索范围、数据缺失、文件及 SHA-256、GitHub commit URL、全库审计、Pages run URL/状态与公开网页链接；状态拆成 `RESEARCH_VERIFIED`、`ARCHIVE_BLOCKED|GITHUB_VERIFIED`、`PAGES_PENDING|PAGES_VERIFIED|PAGES_FAILED`。没有真实工具证据便使用 `UNVERIFIED`。

### 8.8 质量与降级硬门槛

- **不准伪造**：节目稿件完整性、单条时长、新闻镜头、收盘价、北向净流入、公告、企业业务、URL、文档附件、GitHub提交SHA、Actions运行与Pages成功状态。
- **不准时间倒置**：晚间消息与15:00收盘行情分离；未经核验的事件首次公开时间一律 `UNKNOWN`。
- **不准以编排预测收益**：官方报道政治传播权重不等于投资因果强度。
- **不准未检验便发布**：须完成本地完整审计或 PR 全库 CI 成功后才允许 main 合并；CI pending/失败、只提交 manifest 或未知状态都不算已归档。
- **不准删除历史**：新归档必须 preserving 既有 MARKET/TECH/CHINA；同 RUN_KEY 幂等；出现并发更新须重新检索审核后重试。
- **最终评判**：只有“真实研究文件已归档且可以取回 + 全库索引/审计通过 + Pages 真实可访问”才可称网页发布完成。任务定时触发本身只是开始，不是成功。
