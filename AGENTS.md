# AGENTS.md — binding instructions for all scheduled agents

This file is the single source of truth for archival behavior in `1998x-stack/cron-news`. Read it and `README.md` at the **start of every run**, before creating any report. Research instructions remain agent-specific, but repository, publication, QA and delivery instructions here take precedence over outdated archival instructions in the task scheduler.

## Shared contract

1. All scheduled research tasks must run on the assigned Asia/Shanghai schedule. Research -> source and counter-evidence checks -> generate DOCX/PDF/PPTX where feasible -> validate -> archive into GitHub -> regenerate catalog -> full-repository audit -> verify -> one Gmail delivery. **Do not use Notion**: no Notion search, creation, lookup, update, link or success gate. Never silently substitute Notion for GitHub.
2. This repository and its GitHub Pages website are **public**. Publish public research only. Exclude personal addresses, work/internal material, secrets, private data, full paywalled or copyrighted articles, and confidential mail. Attribution and short paraphrase are required. Do not put recipients or credentials in manifests.
3. Deterministic run key: `MARKET-YYYY-MM-DD-0800|1200|2000|2030`, `TECH-YYYY-MM-DD-0800`, `CHINA-YYYY-MM-DD-0800|2000`; use `-MANUAL-HHMM` only for an explicitly manual invocation and preserve this value throughout a run. All date components are the actual Asia/Shanghai calendar date of the scheduled run.
4. Canonical destination: `reports/<agent>/YYYY/MM/DD/<RUN_KEY>/`, where `<agent>` is `market`, `tech`, or `china`. New schema v2: every run MUST contain `manifest.json`, an evidence-based `report.md`, and a machine-readable `data.json`; optional genuine `report.pdf`, `report.docx`, `report.pptx` are permitted. Legacy schema v1 archives (manifest plus verified PDF/DOCX/PPTX) remain read-only and supported. Never publish a blank or invented Markdown/JSON report just to satisfy the schedule. If the primary files cannot be verified and committed, status is ARCHIVE_BLOCKED.
5. Manifest v2 has exactly `schema_version:2`, `run_key`, `agent`, `date`, `scheduled_time`, `title`, `summary`, `status` (`PUBLISHED` for verified substantive research with sources, otherwise `DEGRADED`), `files` (keys `md`, `json` mandatory; `pdf`/`docx`/`pptx` optional; values `{path,bytes,sha256}`). Exactly one `report.md` and one `data.json` per new run. `data.json` uses `schema_version:1`, `run_key`, `agent`, `as_of` (e.g. `2026-11-10T20:30:00+08:00`), `signals` array (title, score or null, confidence, summary), `indices` array (name, value, change_pct or null, as_of, source_url), `sources` array (title,url), and `quality` object (status, gaps). Other evidence-specific fields may be included. Values without authentic sources must be null, not zero or guessed. Legacy v1 manifests retain their original FULL/DEGRADED semantics and are never rewritten. Paths begin with `reports/`, remain repository-relative and forbid other attachments or nested folders.
6. Verify real bytes and magic signatures before publishing: PDF starts `%PDF-`; DOCX/PPTX are valid OOXML ZIP packages, not renamed text. GitHub text file actions cannot substitute for binary uploads. Use an authorized GitHub binary-capable upload path (such as base64 Git blob + tree + commit, or supported Git LFS when appropriate), and verify downloaded bytes and SHA-256. For v2 runs, a GitHub text-file or Git Data API route can publish real Markdown/JSON files without binary conversion; if an optional binary upload is unavailable, omit that format rather than fabricate it. For v1 binary-only runs, lack of verified upload is ARCHIVE_BLOCKED. Avoid GitHub's 100 MiB individual-file limit; prefer much smaller, optimized reports.
7. Use `scripts/build_catalog.py` to regenerate `catalog.json` deterministically from all valid manifests. Never hand-edit the catalog or inline hardcoded report lists in `index.html`. The site reads the catalog and produces links only for files actually recorded. Structured JSON is used for visualization, and old binary-only archives remain downloadable. Preserve past dates and all three agents when adding a new run.
8. Before **every** archive mutation, inspect the current main branch and its full report tree; run `python3 scripts/audit.py` on a complete local checkout with new reports staged. Audit the **entire repository**, not just the new day: no path drift, duplicate keys, duplicate files, orphan binaries, unexpected file types, stale/missing catalog entries, mismatched hashes/sizes, broken relative links, accidental private material, or unrecorded relocation. Regenerate catalog and rerun audit after repairs. On validation failure, do not publish and clearly report the blocker.
9. Commit report files, manifest and regenerated catalog together, using optimistic SHA/fast-forward protection. Check the latest branch SHA first to avoid concurrent 08:00 task writes; if it moved, refresh and rebuild catalog against the latest tree, rerun audit, and retry without force-pushing or losing another agent's report. A run key is idempotent: if already archived and validated, do not create an alternate copy.
10. After committing, check GitHub files and public URLs for PDF/DOCX/PPTX links. Confirm the Pages index is updated; Pages publication may lag, so report repository commit success separately from website availability. Do not treat a failed site build as a successful public delivery.
11. Gmail, only for tasks with an already authorized private delivery configuration: Search `SENT` for the exact run key before any send; at most one send attempt for a given run key, all authorized recipients in the same message. After success, verify message ID, recipients and actual attachments. If a send returns unknown/error, search SENT and mark `DELIVERY_UNVERIFIED` if still uncertain; never blindly resend. Do not leak recipient addresses to this public repository.
12. Each execution ends with a short integrity report: run key, repo commit URL, archived formats, missing formats, catalog validation, full-tree audit result, Pages link status and Gmail delivery status. Never report success merely because the schedule triggered.

## Agent-specific research requirements

### MARKET — daily 08:00 / 12:00 / 20:00 / 20:30
Scan A/H/US indices, rates, FX, commodities and ETFs plus official policy, company releases, international and domestic reporting. Form 8–15 candidate events, select 5–8 verified core topics, and cross-check source facts + actual market reaction + transmission mechanism and counterexamples. 08:00 is overnight/preview, 12:00 compares morning data to 08:00, 20:00 is closing analysis plus available News Lianbo/official policy. 20:30 is the dedicated three-day News Lianbo × A-share policy transmission report. Its primary contract is v2 Markdown/JSON + Pages, not email; do not infer that the other MARKET email delivery settings authorize recipients for this distinct 20:30 task. Do not invent data or claim policy causes a price move merely because both occurred. Allow FULL/DEGRADED/MINIMUM Gmail delivery; MINIMUM email does **not** count as repository archival success.

### TECH — daily 08:00
Scan 24–72h AI/Agent papers, CS conferences, official research and engineering blogs, GitHub releases/PRs/issues/artifacts. Form 15–30 candidates; deep-dive ~3 AI/Agent subjects and 2–4 other CS subjects as evidence permits. Compare methods, datasets, baselines, ablations, costs, reproducibility, counter-evidence and code. Include 1–3 cross-CS bridges plus a learning queue and knowledge map **inside the documents**, not in Notion. Aim for all three verified formats; do not assert successful complete delivery if any required artifact is missing.

### CHINA — daily 08:00 / 20:00
Scan primary official materials, reliable domestic/international coverage and relevant policy, industry, society, macro and international data. Keep 15–30 candidates, deep-dive 3–6 material topics, distinguish confirmed facts vs attributed interpretations and competing explanations, compare the last seven days and identify falsifiable follow-up indicators. 08:00 covers overnight changes, 20:00 covers same-day changes. Keep factual, neutral political descriptions: do not endorse political actors or make electoral forecasts. Allow FULL/DEGRADED/MINIMUM Gmail delivery; MINIMUM email does **not** count as repository archival success.

## Document-entropy gate (mandatory, every run)

- **Placement:** one run = one folder = one manifest; v2 also requires `report.md` and `data.json`. Reject files outside canonical locations, case-fold collisions, `latest`, `final`, `copy`, and duplicate dates or formats.
- **Correctness:** compare actual bytes/sha256 and validate Markdown UTF-8/JSON identity plus binary MIME signatures where present; never link absent files. PDF, DOCX, PPTX remain distinct optional downloadable formats for v2.
- **Index integrity:** rebuild deterministic global catalog from every manifest and compare it byte-for-byte with committed `catalog.json`; report every orphan, duplicate and missing entry. Validate all site hrefs are repository-relative and point to real files.
- **History integrity:** preserve original previous-run paths, verify archive-wide consistency and do not erase earlier published material by replacing a partial catalog. Explicitly record and audit any necessary migration.
- **Public safety:** block accidental private identifiers, credentials and internal documents prior to publication; machine checks are a supplement, not a substitute for review.

If any gate fails, stop publication for that run, retain prior working website, and surface the failure instead of making unverified claims. Update this contract and README together whenever the schema or directory layout legitimately changes.
